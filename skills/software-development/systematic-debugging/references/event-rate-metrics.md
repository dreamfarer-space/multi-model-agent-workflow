# Debugging event-driven rate metrics

Use this recipe for streamed token rates, throughput displays and other sliding-window measurements.

1. Build a fake-clock replay at the tracker boundary. Capture start time, raw event arrival timestamps, amounts and lifecycle transitions. Assert current rate, peak, average and active/paused state independently; one correct field does not establish the others.
2. Trace the denominator through every rate calculation. Perform anomaly detection using the actual measured arrival interval before applying a minimum display interval: padding a short denominator can hide the very burst the threshold is intended to reject. Define zero-span handling explicitly and test timestamps on both sides of the minimum interval. Use tools to calculate expected values rather than estimating them mentally.
3. Inspect early returns and retained state together. Run burst detection before a short-window early return if that return would preserve the anomalous sample. When excluding a burst, advance the window boundary or remove its contribution and establish the correct timing origin for later events; merely returning an absent rate leaves the burst available to inflate a subsequent window and peak.
4. Test a short-interval burst followed by a normal delta using explicit timestamps and token counts. Assert no peak is recorded for the rejected burst, the next rate reflects only the normal delta over its intended interval, and later windows remain clean. Include an ordinary stream case so the filter does not suppress valid samples. Apply borrowed thresholds only after verifying their units and timing semantics match this tracker.
5. Trace pause and resume across producer, snapshot and consumer. Pause at message completion and tool execution as required by the lifecycle. Expose effective streaming state that accounts for pauses, then verify both the status bar and expanded detail display stop showing a stale current rate while retaining valid historical aggregates. Do not erase a legitimate peak merely to hide an inactive rate.
6. Test authoritative usage reconciliation across messages, including a message without usage followed by one with usage. Preserve estimates for unreported messages while replacing the reported message's estimate with its authoritative count; do not overwrite the whole turn and silently lose prior estimates. Keep display-rate filtering separate from token accounting, because an anomalous arrival rate does not make the tokens invalid.
7. Run the tracker reproduction, lifecycle/translator tests and affected display tests. Describe these as automated evidence. Claim provider or desktop manual verification only after actually exercising that path; a fake-clock replay establishes the arithmetic and state behavior within its seam.
