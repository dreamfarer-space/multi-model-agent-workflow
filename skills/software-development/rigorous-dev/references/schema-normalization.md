# Schema normalization and recovery

Use when implementing lenient validation, model-facing repair hints, incremental tool rendering, or schema retry metrics. These are design and regression probes; confirm findings against the current implementation rather than treating a review report as proof of a defect or a proposed fix as verified.

1. Define the accepted transformations before editing. Keep lenient mode opt-in when the product requires it. Enumerate safe aliases, misplaced declared properties and harmless decoration separately from unknown business fields, actions and malformed content. Reject ambiguous transformations or produce an explicit diagnostic; deleting arbitrary unknown data merely to pass validation can change the user's meaning.

2. Establish the mutation contract at every public boundary. Exercise fully frozen inputs and partially frozen nested values such as a single option object. Clone the complete mutable normalization subtree or use an immutable transform; shallow freeze checks cannot establish that nested writes are safe. Check both absence of exceptions and preservation of caller-owned objects according to the declared contract. If normalized output is carried in metadata or a snapshot, assert that it is the representation downstream consumers actually use.

3. Separate local normalization from cross-node conversion. Normalize identifiers and declared properties across all nodes before resolving references or absorbing children, because component-array order must not determine retained content. Test permutations of the same tree. Before absorbing a child, account for descendants, extra content, duplicate identifiers, shared references and references from outside the converted container. Reject unsafe conversion rather than silently dropping content or manufacturing a valid-looking item from an unresolved identifier. Assert semantic preservation separately from a JSON round-trip with no undefined values.

4. Verify actionable diagnostics by executing their examples. Include the expected component contract for missing required fields. Build suggested replacements so an old invalid field cannot override its repaired value through spread order. Extract suggested JSON in regression tests and run it through validation for the advertised repair; use schema-valid examples for enums, minimum array lengths and nested required fields. If a suggestion only repairs one of several defects, say so rather than presenting the whole replacement as valid.

5. Give streaming preview and rejection recovery distinct read modes. Streaming may expose an unfinished tail for incremental display; rejection recovery must select only completed eligible blocks. Test a completed Markdown block followed by an unclosed Markdown string, a partially emitted catalog block, stopped output and a rejected payload. Assert that unfinished text is visible only in the intended streaming state and is excluded from completed-block salvage. Keep restored content within the normal size and content-validation bounds.

6. Exercise normalization followed by a real patch. First render or compose with aliases, misplaced properties or a safe container conversion; then patch a retained normalized node. Assert the host snapshot, accepted patch, version counter, client projection and mounted output agree. Also replay history through supported projection paths, because a successful first-turn validator test cannot prove that later patches use the normalized tree.

7. Define retry metrics from executed events before aggregation. Keep invalid-call count distinct from actual subsequent attempts and define how interleaved successful calls or multiple tools affect attribution. Test at least: one failure with no subsequent attempt, repeated failures ending without recovery, failure followed by success, and success followed by failure and recovery. Exercise the event-to-metric computation itself; testing aggregation of manually populated counters cannot detect a faulty counter formula.

8. Run focused regressions, then the required suite, typecheck and build after all corrective edits. Refresh execution evidence and review against the final diff; measurements or screenshots from an earlier implementation cannot certify later changes. Report remaining gaps as unverified rather than inferring completion from a review verdict.
