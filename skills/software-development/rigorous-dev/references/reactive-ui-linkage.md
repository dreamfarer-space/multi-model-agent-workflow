# Reactive UI linkage: implementation and acceptance procedure

Use this procedure for declarative forms, computed expressions, and components sharing local browser state. Treat it as a design and verification checklist; derive concrete APIs from the checked-out code.

1. Trace the entire data path before editing. Read the protocol validator, expression evaluator, state store, standalone renderer, composed-block renderer, patched-version renderer, and consuming components. Search every caller and test double of APIs whose shape will change. Completion: each accepted binding has a producer, subscription path, evaluator, and rendered consumer.

2. Define state ownership before adding broadcasts. Share declared binding keys under the root tool-call identity while keeping component-private keys scoped to their block and node. Test sibling blocks sharing the same root and unrelated roots remaining isolated; root scope must not silently become session-global. Make subscribers observe the same canonical key used by readers and writers, or a successful write can leave sibling components stale.

3. Resolve defaults and persisted values consistently. Use stored bound values when present and field defaults only when absent; preserve valid false, zero, and empty-string values. Initialize missing bindings outside render and avoid overwriting restored input on remount or patch. Distinguish own keys from inherited properties in state reads, and use safe dictionary construction throughout input collection and evaluation: `constructor`, `toString`, and `__proto__` can otherwise suppress defaults or disappear during assignment. Test these names at initial mount and after editing, because evaluator-only coverage misses state-store and renderer failures. Explicitly define field-level versus form-level binding precedence and test it rather than inferring it from a prop name. Accept a form-level scalar alias only when its publishing semantics are defined; if it aliases a single field, exclude multi-field form aliases from formula scope and reject their use consistently. Completion: every accepted variable has a publisher, and restored input and derived output agree on first render.

4. Carry computed declarations through every supported renderer path. Parse complete and partial payloads, collect current inputs, evaluate dependencies, and expose the result to consumers. Preserve block-local declaration scope even when input state is shared. Test malformed formulas, dependency cycles, missing inputs, and hidden-field semantics according to the protocol. Completion: a bad formula reports an error without crashing independent outputs.
   - Patch a producer block that has no local computed declarations, then edit its field and assert the sibling consumer changes. Derive publishing requirements from composition bindings, because a producer's local formulas do not describe its siblings' dependencies.
   - Track current reachable local fields separately from external composition fields when validating and rendering patches. Maintain a composition-wide view of current block versions and field producers, and make every consumer observe its changes. Exclude superseded originals and obsolete patch cards from publishing; include bindings from the current patched tree. Stop reading a persisted key only after its last producer disappears, because per-block retirement flags cannot establish whether a sibling still publishes it.
   - Test producer deletion with both an untouched sibling consumer and a previously patched sibling consumer. Also test removal of one of two same-name producers, continued edits from the survivor, and a patched producer that keeps its input. Assert rendered output after each transition; initial-mount coverage cannot expose stale ownership or missing version subscriptions.
   - Replay tool events through the portable artifact projector and assert the patched definition and version advance. Pass valid composition context through every revalidation boundary, because a host-approved cross-block formula can otherwise be silently rejected during projection.

5. Resolve bound props before handing them to concrete components. Keep formatted text interpolation separate from raw numeric references, so progress bars and chart points receive numbers while text receives display formatting. Preserve the original specification and validate declarative references at the protocol boundary; check resolved values where the component requires concrete types. Completion: repeated evaluation does not mutate the source tree or feed unresolved objects to numeric rendering code.

6. Integrate dynamic table predicates into the existing pipeline. Specify comparison-prefix parsing and invalid-number behavior; compose the predicate with search, column filters, sorting, paging, and export. Verify the rendered rows and exported dataset use the same filtered view, and clamp or reset pagination when the result shrinks. Completion: changing an input updates rows and visible counts without sending a model prompt.

7. Exercise actual user interaction. Mount a form and dependent progress, chart, text, and table; change an input and assert the rendered outputs. Repeat with producer and consumer in different composed blocks. Add remount/persisted-state and unrelated-root isolation cases. Assert that local changes do not call the model-send callback. Engine-only tests cannot catch a missing renderer subscription.

8. Run focused linkage tests first, then expression/protocol/state regressions, typecheck, and build using the repository's scripts. For imported React counterexamples in a Vitest project whose default environment is Node, declare `// @vitest-environment jsdom` or use the repository's equivalent browser-test configuration, and retain the real fixtures and setup files. Establish a behavioral assertion failure before treating the test as a reproduction; missing DOM globals and teardown errors are setup failures. Run the full suite at the integration boundary and record actual failures or skips. Review the resulting diff before handing the next phase its base revision; do not call planned behavior verified until these checks execute.

9. Validate block patches against current composition-wide name constraints. Carry or reconstruct the sibling computed identifiers and current field producers at the host validation boundary; a block's own tree and a cached list of field names cannot detect every cross-block collision. Test both rejection of a field colliding with a sibling computed identifier and acceptance of a distinct new field when the protocol permits it. If the available snapshot lacks enough context, make that limitation explicit rather than presenting a blanket ban on new fields as equivalent collision validation.

10. Check the published tool schema and examples against the implemented contract. Show interpolation in string-valued slots and computed references in supported numeric slots; describe dependency ordering according to actual forward-reference support. Accepted payloads, renderer behavior, and model-facing guidance must agree, or generated interfaces can fail despite passing hand-written tests.
