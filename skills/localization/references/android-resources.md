# Android native resource generation and validation

Use when localizing Android notifications, foreground services, or resources emitted by an Expo config plugin.

1. **Trace the display path and resource owner.** Locate the Kotlin/Java code that renders the text and its `R.string` lookups, then locate the config plugin or other generator that writes those resources. Search both normal and fallback paths for hardcoded text. Change the generator when XML is generated; editing a generated Android directory alone loses the fix on the next prebuild.
2. **Preserve the resource contract.** Keep resource IDs consistent between native callers and every emitted locale. Preserve positional format tokens such as `%1$d` and their argument types. Check the generator's actual language/region mapping, including default resources and Chinese region variants; app-level locale coverage does not prove native coverage. Route default task statuses and relative-time labels through resources, and retain a system-localized date fallback if the implementation already provides one.
3. **Check escaping at each layer.** Inspect the generator source, the resulting JavaScript string value, and the emitted XML separately. Android string resources require apostrophe escaping, including French contractions. XML entity escaping alone does not guarantee AAPT accepts an apostrophe. Ensure the emitted XML retains the Android backslash escape; JavaScript can consume that backslash unless the source escapes it too. Use the repository's existing XML escaping helper where available and inspect its actual output before changing it.
4. **Run checks in increasing scope.** Run the existing generator/check command, inspect representative generated resources containing apostrophes and placeholders, then run native resource compilation or a release APK build. For example, run the workspace Android package check script (e.g., `pnpm --filter <android-pkg> check`) to validate the JavaScript/TypeScript side, and use the applicable CI Android packaging job to confirm AAPT/native compilation when relying on CI. Follow the repository's test policy rather than adding tests that merely assert resource strings exist.
5. **Inspect the final packaged strings when artifact-level evidence is needed.** Run the installed SDK's `aapt2 dump resources <absolute-path.apk>` and save the output to scratch. Parse resource blocks by exact `string/<resource_id>` and retain every locale/value pair, including default and region variants; count coverage programmatically rather than truncating search output. This inspects the compiled APK and can confirm that apostrophes and positional placeholders survived packaging. Bind the APK to the verified build head. Treat the result as packaged-resource evidence only: it cannot establish which locale a running service selected or supply a requested screenshot.
6. **Report each validation boundary accurately.** Type checks, JavaScript tests, and a Hermes export do not establish native resource compilation. A successful APK build establishes compilation, while actual notification appearance, selected language, lock-screen behavior, and deep-link navigation require runtime verification. Bind CI evidence to the final PR head or its test merge commit and state only the layers actually exercised.
